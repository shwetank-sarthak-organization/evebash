EVEBASH ACTIVE ISSUES
=====================

How to use this file (people and Claude sessions alike):
- Read this file before starting work, and check whether your change fixes or touches any issue here.
- New issue: add it at the end of ACTIVE ISSUES with the "Next issue number" below, then increase that number by 1.
- Numbers are never reused. If #1 is fixed and removed, the next new issue still takes the next number.
- Starting work on an issue: set Status to "In progress" and Owner to your name.
- Fixed (merged to staging): move the whole entry to RECENTLY FIXED, set Status to "Fixed", and add
  "Fixed in: 9dbddbed (YYYY-MM-DD)". Delete entries from RECENTLY FIXED once they are older than 7 days.
- Dates are YYYY-MM-DD.

Field values:
- Platform:   App | Website | Both | Analytics dashboard   (backend, Modal or database work is noted in the issue text)
- Priority:   Critical | High | Medium | Low
- Status:     Open | In progress | Blocked | Fixed
- Owner:      a name, or Unassigned
- Blocked by: what it waits on (a decision, another issue, a person), or "-"
- Found in:   where it was spotted (an audit, a tester report, a chat)

Note 2026-11-15: cause found, fixed in eb096f18 + f55b4d38 (Android only). React Native's Android HTTP client (OkHttp, no timeouts) never checks that a pooled HTTP/2 connection is still alive. When the network path to Supabase dies silently (no reset reaches the phone, e.g. a Wi-Fi/NAT drop or the phone sleeping), every later request is sent down that dead connection and hangs until lib/supabase.ts aborts it after 20 s. The abort doesn't mark the connection broken, so this repeats until the app restarts. Reproduced on the Mac with the same library (OkHttp 4.9.2 and 4.12.0, React Native's settings) against staging Supabase, through a relay that silently drops the connection: 4 of 4 requests after the drop hung 20 s and no new connection was tried. Fix: config plugin apps/mobile/plugins/withOkHttpHealthPings.js (in app.json) gives React Native's client an HTTP/2 ping every 5 s; otherwise it is the default client (cookie jar, 10 MB cache, no timeouts). OkHttp then fails a dead connection within 10 s, inside the app's 20 s limit, and retries the request on a new one: in the same test the request in flight came back 200 in about 9.5 s (both OkHttp versions) and the next ones took about 50 ms. A 4-minute idle run with the pings kept the same connection to staging Supabase (the server doesn't mind them). Other native clients don't need the change: images (expo-image), video, audio and photo uploads (expo-file-system) use OkHttp with read timeouts, which find a dead connection by themselves (10 s; 60 s for upload chunks); only React Native's client has none. It is a native change, so it needs a new app build (an over-the-air update won't carry it). Checked: the USB dev build of EveBash Staging on the Pixel 8 has the code (dexdump, interval 5) and loads the dashboard from staging normally. Left: device test #216 on a new build.

Issue: The media worker on media.evebash.com (cloudflare-worker/evebash-media-worker/worker.js) never passes the viewer's Range header on to B2: it sends only Authorization and Accept. So a request for part of a file gets the whole file (200, not 206), while the reply still says "Accept-Ranges: bytes". HLS streams are not affected (players fetch whole segments). Plain MP4 playback is: the raw-video fallback in src/components/ui/HLSVideoPlayer.tsx (used when an HLS stream fails), the Vault video preview (src/components/vault/VideoPreview.tsx, if its link goes through media.evebash.com), and resuming a big download. Safari and iPhones need partial replies to play or seek an MP4, so those probably fail there (not checked on a device). B2 itself answers Range correctly (206, checked directly on B2 on 2026-10-29). Fix idea: pass the Range header to B2 behind a worker var (e.g. MEDIA_FORWARD_RANGE), keep Range requests out of the edge cache as today, add Range to Access-Control-Allow-Headers and Content-Range to Access-Control-Expose-Headers, then play a raw MP4 in iPhone Safari.
How to reproduce: curl -A "Mozilla/5.0" -H "Range: bytes=0-99" -o /dev/null -w "%{http_code} %{size_download}\n" https://media.evebash.com/<a video's storage_key> prints "200 10961412" (the whole file) instead of "206 100".
