EVEBASH ACTIVE ISSUES
=====================

How to use this file (people and Claude sessions alike):
- Read this file before starting work, and check whether your change fixes or touches any issue here.
- New issue: add it at the end of ACTIVE ISSUES with the "Next issue number" below, then increase that number by 1.
- Numbers are never reused. If #1 is fixed and removed, the next new issue still takes the next number.
- Starting work on an issue: set Status to "In progress" and Owner to your name.
- Fixed (merged to staging): move the whole entry to RECENTLY FIXED, set Status to "Fixed", and add
  "Fixed in: <commit> (YYYY-MM-DD)". Delete entries from RECENTLY FIXED once they are older than 7 days.
- Dates are YYYY-MM-DD.

Field values:
- Platform:   App | Website | Both | Analytics dashboard   (backend, Modal or database work is noted in the issue text)
- Priority:   Critical | High | Medium | Low
- Status:     Open | In progress | Blocked | Fixed
- Owner:      a name, or Unassigned
- Blocked by: what it waits on (a decision, another issue, a person), or "-"
- Found in:   where it was spotted (an audit, a tester report, a chat)

Found in: Burst-load review of the video pipeline (chat 2026-10-27)
Issue: A backlog of videos makes the watchdog re-send them and then mark them failed. apps/backend/src/services/watchdog.ts (every 10 min) treats any video still in 'processing' 15 min after upload as stuck, re-enqueues it (up to 3 times) and then sets status 'failed'. But Modal caps the video workers (transcode_video_short max 10, long-video GPU 5 + 16-core 5), so in a burst (e.g. 30-50 long recordings from a wedding) videos simply wait in Modal's queue for longer than 15 min. The re-enqueue is not deduplicated (QStash's dedup window is 10 min and the watchdog fires later), and the Modal lock (video-transcode-locks) only skips a copy while the first one is running: a copy that starts after the first finished transcodes the whole video again (double cost, more backlog, more re-sends). After 3 rounds (~45 min) a still-waiting video is shown as failed, then flips to processed when its real run finishes.
How to reproduce: Code check (watchdog.ts lines 31-90, modal_engine/main.py _transcode_once). Load test: upload 20+ videos over 10 min to one gallery and watch transcode_attempts and modal_cost_logs for duplicate process_video_* rows per photo.
Fix idea (behind a flag): measure "stuck" from when a worker actually starts (worker writes processing_started_at / a heartbeat), not from upload; skip re-enqueue while the video-transcode-locks entry exists or the Modal call is still queued; make _transcode_video_core return early when the row is already 'processed' for the same storage_key.
Fix plan (2026-10-27): 1) the worker writes processing_started_at when it really starts and a heartbeat every minute; 2) the watchdog re-sends only when the job is not waiting and not running: for RunPod jobs (todo #18) it asks RunPod /status (IN_QUEUE or IN_PROGRESS = leave it), for Modal jobs it checks the lock and the heartbeat; 3) the worker returns early if the row is already processed or master.m3u8 exists; 4) the app shows "waiting in line" instead of failed while a job is queued, and 'failed' is set only after 3 real failed runs, not after waiting time. All behind a switch, off by default.
Built 2026-10-27, code on staging in cb8cda4, Modal v133 deployed 2026-10-27 (migration not applied; both switches off by default, so nothing changes until they are turned on):
- supabase/migrations/20261027000000_video_transcode_heartbeat.sql (NOT applied): photos.transcode_queued_at and photos.transcode_heartbeat_at, both NULL unless the Modal switch is on.
- modal_engine/main.py, key "queue_aware" of the video switch (modal_engine/video_gpu_switch.py queue-aware on|off): the QStash endpoints write transcode_queued_at after they start the job, and so do both GPU-to-16-core handovers; _transcode_once writes transcode_heartbeat_at at start and every 60 s while the worker runs; after taking the lock it skips the job when the row is already processed and its url is this file's hls/<storage_key>/master.m3u8. Any DB error: logged, and the video is handled as before.
- apps/backend/src/services/watchdog.ts, VIDEO_WATCHDOG_QUEUE_AWARE=true: leaves a video alone while its heartbeat is under 10 min old, or while it was queued after its last heartbeat and less than 2 h ago; otherwise re-sends it, and marks it failed only after 3 such re-sends. Reads 200 rows instead of 20. Without the migration it reports that and uses the old rule.
- Differences from the fix plan: "already done" is read from the row (status + url), not by listing B2; no separate "waiting in line" label in the app or website: a waiting video now stays "processing" instead of turning "failed".
- Tests: apps/backend/tests/watchdogQueueAware.test.ts (decision rule; backend suite 109/109 pass); a full watchdog run against a fake database (off = old behaviour, on = waiting/running left alone, migration missing = old rule) and the Modal worker changes against fake Modal dicts and a fake database (off = no writes and no skip; on = heartbeats, skip of a processed copy, lock still works, DB errors fail open) both passed locally.

Rollback: VIDEO_WATCHDOG_QUEUE_AWARE=false and queue-aware off (no deploy).
